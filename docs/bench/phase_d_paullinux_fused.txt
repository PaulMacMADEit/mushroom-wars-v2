Throughput observations:
- Fused K=1: 1.77× over per-tick on identical work — pure overhead win
  from collapsing 64 chunk-pulls into the same 64 chunk-pulls but with
  one host snapshot reused for opponent + mask + obs (vs the per-tick
  adapter doing it twice per tick).
- Fused K≥4: scales with K because the ~10ms/chunk Python-host loop
  (mask compute + opponent + obs.copy + RunningNorm) gets amortised over
  more env ticks. K=8 is the sweet spot for this n_envs (45us/tick).
- K=16 keeps improving but hits diminishing returns; agent is making
  fewer decisions per rollout, which weakens PPO's on-policy bound.

GPU SM observations (10-update fused K=8 run, ~256s wall):
- nvidia-smi dmon -s u sustained mean SM ≈ 3% over the whole run.
- The 3070 kernel finishes each chunk in <50ms; the rest is host work
  (Python loop + numpy mask + RunningNorm + agent.act_batch round-trip).
- This MISSES the FUSED_ROLLOUT_PLAN §1 criterion 4 (GPU SM mean ≥ 30%).

Where the missed gate goes:
- The current path still pulls obs to numpy every chunk, runs torch on
  cpu-resident-but-cuda-tensorised inputs (cuda kernels are tiny → host
  dominates), normalises in numpy, and pushes back. DLPack JAX↔torch
  zero-copy on the same CUDA device (Phase E in the plan) is the way to
  remove the bulk of that round-trip.
- Phase E was marked OPTIONAL in the plan, gated on Phase D's profile
  showing the round-trip mattered. It does. It's the next piece.

Training quality:
- Fused K=8, 10 updates, n_envs=1024 — reward climbs 0.011 → 0.134
  monotonically; eps_per_update grows 3076 → 5316 (model winning faster).
- Algorithm is working; this isn't a correctness regression.
