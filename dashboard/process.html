Process — what one training run actually does

This page walks one training run from the moment something queues it to the moment it lands on the leaderboard. Every number on this page comes from the actual config / code — see the file references at the bottom of each section.

Last updated: 2026-04-29. If a number here disagrees with the code, the code wins.

1. Where runs come from

There are three sources that drop a row into the runs table with status = "queued". A worker daemon then picks it up.

Acron-agent (every 3h) scripts/cron_agent_pulse.py

A systemd timer fires every 3 hours and runs the cron-agent. The agent checks the curriculum phase (phase1_full_mix or phase2_selfplay) and queues a batch shaped like:

  • 6 short cells (~15 min each)
  • 4 medium cells (~30 min each)
  • 3 long cells (~60 min each)
  • 1 endurance cell (~60 min)

Total wall budget per cron fire is roughly 6 hours of compute. The cron-agent also runs Elo review and curriculum graduation checks, but only AFTER queuing the batch (so the worker never sits idle waiting for analysis).

Bkarpathy-loop (Claude self-paced) configs/karpathy_loop.yaml + scripts/queue_karp_sweep.py

A separate sweep loop fires roughly every 30 minutes. It reads karpathy_loop.yaml, takes the next sweep axis (e.g. lr, entropy_coef, gamma, reward_version), and queues 3 cells (lo / mid / hi) at cell_budget_seconds = 600. One variable changes; everything else is held at baseline. This is where most of the recent karpv2-* runs come from.

Cmanual scripts/queue_b6.py / queue_v13_validation.py / etc.

Hand-written scripts for one-off experiments — for example "queue 4 endurance runs at 90 min vs the b3 champion across seeds 1/2/3/42".

3. Picking the level + opponent

3a. Level — what map you train on

Each of the 1024 envs samples a level independently on reset, so a single rollout step can have envs running 4-building games and envs running 24-building games at the same time. Two ways to specify:

  • Single level via level_name — e.g. random_close_4_5 (350×350 map, 4–5 buildings, ~half travel time of full map).
  • Mix via level_mix — e.g. {random_4_8: 0.20, random_6_10: 0.20, random_8_16: 0.30, random_16_24: 0.30}. That's the b6 phase1_full_mix recipe.

Generators live in sim/levels.py. random_close_* is a small map; random_* is the full 700×700 map; asym_* is intentionally unfair (P1 starts closer to neutrals).

3b. Opponent — who plays P2 against the learner's P1

Set by opponent_name on the queue row. Five legal values:

random_legal
JAX-on-device uniform-random pick over legal moves. Free (no extra net inference). The default opponent until 2026-04-29.
noop
P2 does nothing. Never used in real training; only for sanity checks.
neural
A frozen past checkpoint loaded once at run start. P2 obs go through the opponent net to pick a move every action_repeat ticks. Currently scalar-per-env on host — this is the karp v2 bottleneck.
latest_champion
Sugar. queue_karp_sweep.py resolves it to opponent_name=neural with the current top champions[0].source_run_id.
self-play pool (when self_play=true)
The trainer keeps a pool of past snapshots of itself. With probability leaderboard_bias (default 0.30) it samples from the champion archive with PFSP weights (target 50%-win-rate opponents); otherwise it samples from the run's own self-play pool, with latest_bias = 0.8 favouring the most recent snapshot. Note: requires self_play=true; karp v2 has it false, so PFSP is currently inactive in karp.

Source: training/trainer.py:_refresh_opponents(), training/fused_rollout.py:_pack_action_batch_*, sim/levels.py.

4. Collecting one rollout

With n_envs = 1024 and rollout_steps = 64, one rollout produces 1024 × 64 = 65,536 (obs, action, reward, value, mask) samples before any learning happens. The per-step inner loop:

  1. Encode the 1024 P1 obs from device-side state to a fixed-shape tensor (training/encoder_jax.py).
  2. Compute mask of legal actions per env, on device (compute_mask_batched_jax).
  3. Learner forward pass — the v9.0-1024 net runs on all 1024 P1 obs in one batched torch call. Outputs source / type / target logits + value.
  4. Sample P1 actions under the legal mask.
  5. P2 actions — depends on opponent:
    • random_legal → JAX uniform sample over the P2 mask, on device. Free.
    • neural / latest_champion → snapshot 1024 states to host, loop scalar over each env, encode P2-mirrored obs, run opponent net, pack actions back. slow path
  6. step_chunk — sim advances K=2 ticks per env, returns (next_state, reward, done). Auto-resets done envs.
  7. Append to rollout buffer. Repeat 64 times.

With random_legal opponent on a JIT-warm RTX 3070, this loop runs at ~2.7-4.7K sim-steps/sec end to end. With latest_champion in the current scalar-per-env path it drops to ~322 steps/sec.

Source: training/fused_rollout.py:collect_rollout_fused().

5. PPO update — what learning means here

After the 65,536-sample rollout buffer is full, the trainer does ONE PPO update. That update is update_epochs = 4 passes over the buffer, chopped into minibatch_size = 512 chunks → 4 × 128 = 512 SGD steps per update. Each step:

  1. Compute advantages (GAE λ=0.95, γ=0.97), normalize across the buffer.
  2. Forward pass on the minibatch → new log-probs, entropy, value.
  3. Clipped policy loss: min(r·A, clip(r, 1-ε, 1+ε)·A), ε = 0.2.
  4. Critic loss: plain MSE between predicted value and GAE return. no value-clipping yet
  5. Total loss = policy + 0.5 · value − 0.01 · entropy.
  6. Adam step. Gradient norm clipped at 0.5.

What gets logged per update (you can plot any of these):

  • policy_loss, value_loss, entropy_loss
  • approx_kl, clip_fraction, grad_norm
  • explained_variance — 1 − Var(returns − values) / Var(returns). ~1.0 = critic perfect, ~0 = no better than mean, < 0 = critic worse than predicting the mean. The early-warning signal for value-head collapse.
  • mean_reward, win_rate (over completed episodes in the rollout)
  • episode_return min / max / p10 / p50 / p90 — variance bands, not just the mean.

Source: training/trainer.py:_update_from_batch() ~line 480-570.

6. The training loop — how a "cell" actually runs

A cell has a wall budget (cell_budget_seconds) — 600s for karp cells, 900-3600s for cron cells. The trainer just loops:

  1. Refresh opponents (resample champion archive every 16 updates by default).
  2. Collect one rollout (§4).
  3. Run one PPO update (§5).
  4. Every SNAPSHOT_INTERVAL_S = 600s, save a snapshot to models/snapshots/<run_id>/<n>/weights.pt. Available for later PFSP sampling but NOT auto-evaluated.
  5. Check wall clock. If > budget → break.

At random_legal + 1024 envs + 64 rollout_steps, one update takes roughly 15-25 seconds, so a 600s cell gets ~25-40 updates and ~1.6M-2.6M decision samples. At latest_champion (current scalar path), the same cell gets only 3-5 updates — that is the karpv2 problem.

7. End of training — what happens at mark_done()

  1. Trainer writes the final weights + obs_norm to S3 / Supabase storage.
  2. Worker calls mark_done(run_id) → status = done.
  3. Worker calls _auto_rate_run(run_id) — runs 3 matches × 64 games vs random_legal, writes initial Elo. So every run lands on the dashboard with a rating within ~5 minutes.
  4. Worker calls workers.bench_eval.run_bench_eval(run_id) — see §8.

8. bench_eval — Elo + promotion workers/bench_eval.py

bench_eval is the truth-of-record for "is this run any good?". It runs every finished training run through three stages:

8a. Bootstrap gate (skipped once archive ≥ 3)

  • 30 games vs random_legal.
  • Win-rate ≥ 0.70 → seed into champion archive.
  • Below → elo_status = "did_not_perform"; the run is shown but not used as an opponent.
  • Once the archive has 3 entries, this gate is never queried again. random_legal stops being a yardstick.

8b. Archive sweep — fills bench_vector

  • For each champion in the archive (cap 20): play SWEEP_GAMES = 8 games head-to-head. Sides alternate every game so P1-advantage cancels.
  • Result is written to runs.bench_vector as {champion_id: win_rate}.
  • Each match also fires update_elo_from_match with K = 32 — so each pair of runs nudges Elo once per sweep based on its 8-game aggregate.

8c. Promotion vs current champion

  • PROMO_GAMES = 16 head-to-head vs the most-recent champion.
  • PROMO_THRESHOLD = 0.60 → promote (snapshot OLD champion into the archive, NEW becomes the live champion). Archive is pruned to cap 20, soft-cap 10 per arch_era; busiest era's oldest is evicted first.
  • Below 0.60 → no promotion, run still has its bench_vector + Elo.

8d. PFSP weight

After the sweep, the trainer computes pfsp_weight = harmonic_mean(1 - |wr - 0.5|) across the bench_vector. Peaks at 50% win-rate (max info), drops toward 0 / 1 (already-solved or hopeless). Used by future training runs that have self_play=true to bias opponent sampling toward "interesting" archive members.

Tunables at workers/bench_eval.py:52-65: SWEEP_GAMES=8, PROMO_GAMES=16, PROMO_THRESHOLD=0.60, BOOTSTRAP_GATE_GAMES=30, BOOTSTRAP_GATE_THRESHOLD=0.70, MAX_ARCHIVE_SIZE=20, ELO_K=32, LEVEL=random_8_16, MAX_TICKS=200.

9. Periodic re-rating

  • Anchor at 1000. 1000 = pure-random_legal play. > 1000 = beats random. < 1000 = worse than random.
  • Sunday weekly rerate (mushroom-rerate.timer, Sun 02:13 PT) — top 30 runs play 4 matches × 64 games against each other. Refreshes the leaderboard against drift.
  • Version-triggered rerate. Calling register_model.py ... --trigger-rerate sets kv['needs_rerate']='1'. Next cron-agent fire kicks off rate_all_runs.py once and clears the flag. Use after a major model bump.

11. Where measurement noise comes from

Useful framing when you read the dashboard: every Elo number is the output of a small number of games, and small-sample win-rates have wide confidence intervals.

DecisionGames used95% CI on a measured 0.5095% CI on a measured 0.60
Auto-rate at finish (vs random_legal)3 × 64 = 192±7 pp±7 pp
bench_vector entry (per archive member)8±35 pp±34 pp
Promotion vs current champion16±25 pp±24 pp
Bootstrap gate (one-time)30±18 pp±18 pp
Sunday rerate match4 × 64 = 256±6 pp±6 pp

Reading: with PROMO_GAMES = 16, a measured 0.60 win-rate against the champion has a 95% CI of roughly [0.36, 0.81]. That means a single 16-game promotion decision is barely distinguishable from random fluctuation, especially when most candidate runs cluster near 0.50. The auto-rate-at-finish is much more stable because it uses 192 games.

K-factor is 32 in bench, so each match nudges Elo by up to ±16 points based on an 8-game or 16-game aggregate. A single unlucky 8-game block can shift a run's rating by 10-15 Elo for reasons unrelated to learning.
